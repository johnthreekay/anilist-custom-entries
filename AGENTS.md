# AniList Custom Entries: full reference

This is the long-form documentation (behaviour, internals, every option). The short human-facing overview is [README.md](README.md).

A userscript that lets you create **fully client-side custom entries** on [AniList](https://anilist.co), for doujins, web novels, fan works, or anything else that isn't in the AniList database. Custom entries behave exactly like normal list entries: they live in your status lists and custom lists, and you can rate them, track progress, add notes, favourite them, and delete them through AniList's **native UI**. They also show up in the home page's **Anime/Manga in Progress** panels and generate **local activity feed entries** ("Watched episode 5 of …") that render natively in your home and profile feeds.

Nothing about a custom entry ever touches AniList's servers, everything is stored in your browser's `localStorage`, optionally synced across devices through a private GitHub repo (see below).

## Install

1. Install [Violentmonkey](https://violentmonkey.github.io/) (or Tampermonkey).
2. Open **[anilist-custom-entries.user.js](https://raw.githubusercontent.com/johnthreekay/anilist-custom-entries/main/anilist-custom-entries.user.js)** and confirm the install. The header carries `@updateURL`, so the manager picks up new versions on its own from then on (Violentmonkey checks daily by default; "Check for updates" forces it).
3. Open your anime or manga list on anilist.co once (the script learns your user id from the list response).

The header grants `GM_xmlhttpRequest` (with `@connect *`) for the import sources that don't send CORS headers and for image embedding, accept the cross-origin prompt if your manager shows one. Granting anything sandboxes the script, so it runs with `@inject-into page` (Violentmonkey) / `@sandbox raw` (Tampermonkey) and aliases `window` to `unsafeWindow` internally: the page-level `fetch`/`Worker` hooks it depends on keep working. If you edit the header and drop the grants, everything still runs, the three GM-only sources just report themselves unavailable.

## Usage

- On your **Anime List** or **Manga List** page, two small buttons sit in the sidebar next to the “open random list entry” die button, colored with your AniList profile color: **“+” creates** a custom entry, **“🔧” (wrench) manages** them (entry list, account move, Export/Import, GitHub sync).
- **Creating**: the “+” modal has a search box that queries **MangaBaka, MangaDex, Dynasty Reader, RanobeDB and MAL (via Tenrai)** in parallel (manga), or MAL (anime). Results show a cover thumbnail, type, year, authors and a source badge so near-identical titles can be told apart, **click the one you want** to fill the whole form: title + synonyms, hi-res cover, description, release status, chapter/volume/episode counts, genres, tags, studio, start year, plus **characters with images from MAL** (Main + Supporting, flipped to natural name order). MangaBaka results chain to MAL characters automatically when a MAL id is linked. Banners stay manual (neither source has AniList-style banners). After a MangaBaka pick, a **“Choose Cover…”** button under the cover field opens a thumbnail grid of MangaBaka's per-volume/season cover art with volume + language labels, a language filter, and paged “Load More” (24 per page). Nothing is saved until you press Create, and external ids (`mangabaka`/`mal`/`mangaupdates`/`anilist`) are stored on the record for future re-sync. One source erroring never hides the other's results: each source reports its own failure inline (“source unavailable (504)”, “rate limited, wait a moment (429)”), and server errors are retried once.

You can also fill everything manually: title, format, list status, **release status**, counts, cover/banner URLs, **description** (basic HTML works), **genres**, **tags** (`Name:rank`, comma-separated), **studio** (anime), and **characters**.
- **Import sources** (manga): MangaBaka and MAL are queried with plain `fetch`; **MangaDex, Dynasty Reader and RanobeDB** send no CORS headers for anilist.co, so they go through `GM_xmlhttpRequest` (anonymous, no cookies). (MangaUpdates isn't queried separately: MangaBaka already aggregates its database and carries the MU id.) Dynasty and RanobeDB search results are thin, so picking a row first fetches the full record (“Fetching details from …”), status, authors, alt titles, tags, description, before filling the form. Dynasty has no search API: its HTML search page is parsed (Series, Anthology and standalone Chapter results, numbered chapters of a listed series are dropped) and the pick is hydrated from Dynasty's per-item `.json`; a standalone chapter imports as a **One-shot** with the doujin parent, page count and scanlator noted in the description and its first page as the cover. Dynasty's own tags are sparse (often one genre plus a pairing, that's all the site has, not a parser gap), so the import also adds the pairing at rank 70 and the doujin parent + `Doujinshi` at rank 60 as tags. RanobeDB imports as **Light Novel** and carries the MAL id, so MAL characters chain automatically; MangaDex carries MAL/AniList ids from its links. Rows whose source knows an AniList id are marked “already on AniList”, a hint that a custom entry probably isn't needed. Genres and tags from every source are canonicalized against AniList's own vocabulary: `splitGenresTags` (now used by every provider — MangaBaka and MAL previously passed vocab through raw, and MAL demographics wrongly became genres) maps genre-equivalents into the fixed genre list, and `canonTag` renames tags to their catalog form via `catalogTagLoose` (exact then squashed `tagKey` lookup against the cached `MediaTagCollection`) or the curated `TAG_ALIAS` table (an alias only applies when its target exists in the catalog, so a wrong guess is a no-op). Unmatched names — Dynasty pairings, "Aaaaaaangst", scanlator vocab — are preserved verbatim with their `:NN` ranks, never dropped; unranked import tags get a descending 90/88/86… band (floor 40) instead of a wall of 100%s. Imports also fill `rec.staff` when it's empty (`importStaff`; never clobbers curation): providers with roles keep them (`staffRows` — MangaDex author/artist → Story/Art/Story & Art, RanobeDB author/illustrator → Story/Illustration; MAL names flipped from "Last, First"), roleless sources give a solo author "Story & Art". `mergeExternal` skips null provider ids so one source can't erase ids learned from another, and `romajiScore` treats English function words that happen to scan as Hepburn ("Bloom **Into You**") as English evidence (`ENGLISH_HINTS`), while MangaBaka's camel-cased single-token `romanized_title` abbreviations ("YagaKimi") are rescued with the full romanization from the alt-title bag. An unknown source status never fabricates "Releasing": normalizers emit `mediaStatus: null` and `applyImportToRec` keeps the record's status; a stale MangaBaka record (status `unknown`) also drops its chapter/volume counts and gains a `hydrate` that asks the upstream MangaUpdates record (`muFetchJson`, base-36 id → numeric, `completed: true/false` → Finished/Releasing) — pick flows and bulk import run `hydrate` before applying. Dynasty anthologies are Finished collections, so their chapter count applies. MAL's taxonomy is tiny (twenty-ish genres plus a few themes; doujins often carry nothing), so MAL-sourced manga chase their MangaBaka record — `mbByMalId`, a title search verified by exact MAL id — for the richer MangaUpdates-derived tags and source ids: `mergeTagsFrom` is an add-only union (never removes or re-ranks existing tags), run on MAL search picks (panel + creation modal) and after bulk-import detail fetches.
- **Covers/banners from hotlink-blocking hosts are embedded.** Some hosts (Dynasty Reader, most image boards) return 403 when the Referer is anilist.co, so their image URLs render broken all over AniList. Before a cover/banner URL is stored (create modal, quick-edit Save, cover picker, MangaBaka/other imports, and the native submission form's Submit) the script test-loads it the way AniList's own `<img>` would; if that fails, or if a Referer-less load of the same URL comes back with different dimensions, i.e. the host swaps in a decoy for hotlinks the way MangaDex's `uploads.mangadex.org` does (200 OK, "you can read this at mangadex.org"), which is also on a small always-embed list, it fetches the bytes out-of-band (`GM_xmlhttpRequest` → CORS `fetch` without Referer → the `images.weserv.nl` proxy as a last resort, only the image URL is sent there, and note weserv refuses some hosts incl. dynasty-scans.com; set `IMAGE_PROXY` to `null` in the script to disable) and stores a **`data:` URI**, so the record is self-contained. Encoding: files ≤150 KB are stored verbatim; larger ones are downscaled on a canvas (covers ≤400×600, banners ≤1900×600, JPEG, typically 40–120 KB). A toast reports the swap. Hosts that hotlink fine cost one probe per session. In the quick-edit panel an embedded image shows as “[embedded image, paste a URL to replace]” rather than the base64 blob, with the source URL in the field's tooltip.
  - **Firefox fingerprinting protection (RFP, LibreWolf, Tor Browser; also FPP canvas randomization)** answers canvas readbacks with noise/blank data unless the site is allowed to read canvas, which would store garbage. The script probes the canvas once per page (two solid fills must encode tiny and different) and, if it looks spoofed, never encodes through it: small files are stored verbatim, the image proxy is asked to resize server-side where it accepts the host, files up to 400 KB are stored un-resized, and beyond that the embed fails with a toast asking you to **allow canvas for anilist.co** (the prompt/icon appears in the URL bar when you press Save/Create/Embed, since Firefox only shows it for reads made during a user gesture). After granting, press **Embed** to redo the image.
  - **Embed button** (quick-edit panel, next to Cover/Banner URL): force-embeds the URL in the field even if the host hotlinks fine, or, when the field is empty or shows the embedded marker, re-embeds from the remembered source URL (`coverSource` / `bannerSource` on the record, kept whenever a real URL is stored). So an embed can be redone (e.g. after granting canvas) or brought back after the field was cleared or replaced.
- **MAL data comes from [Tenrai](https://tenrai.org/) (`api.tenrai.org/v1`), not Jikan.** Jikan's public API now fails constantly, its own MyAnimeList upstream refuses connections, so search 504s more or less permanently ([jikan-rest#610](https://github.com/jikan-me/jikan-rest/issues/610)), and it shuts down entirely on **2026-10-01**. Tenrai is its stated successor and its v1 schema is a continuation of Jikan v4, so the switch was a base-URL change with no parser edits.
- On **Create**, the **native AniList list editor** opens automatically, score it, write notes, tick custom lists, set dates, favourite it, all natively. Every later interaction (edit button on rows, the “+” progress button, the media page status dropdown, delete) also works through AniList's own UI.
- Clicking a custom entry opens a working (local-only) media page: description, genres, rank-sorted tags, a Characters section and tab, and studio all render natively. (Newly added characters show up on the next page visit.)
- **Editing media details happens on AniList's own submission editor** (`/edit/<type>/<id>`), reach it from the **“✏ Edit Custom Entry” button** in the media page sidebar or by clicking an entry in the wrench manage modal. The native form is pre-filled from the local record, and Submitting applies the changes locally, the “Submission sources & notes” field is filled in automatically. The **Characters** section lists local characters, and role changes / “Create New Character” / “Add Characters” (including linking real AniList characters) / deletion are all handled locally. The **Staff** section works the same way: “Add Staff” searches AniList's real staff and links them with a role (name/image/language fetched once and stored on the record; a person can hold several roles), “Create New Staff” creates a local staff person (with a working local `/staff/<id>` page listing their roles on custom entries), roles are editable and the trash button unlinks; the media page then shows a native Staff section and Staff tab, with cards linking to the real staff page (or the local one). **Relations** and **External Links** work too: “Add Relation” (its search lists your other custom entries alongside AniList's, so custom ↔ custom relations work, and the relation-type dropdown gains **Parent**, which AniList's own form lacks: the target gets the reciprocal edge and both edit pages and both entry pages show the pair, and removing it on either side removes both; real targets get a media stub) and “Add Link” (site, URL, notes; colour/icon filled from AniList's link-source catalog) save locally on Submit, and the media page shows them natively; existing edges/links are pre-filled in the form for edits. AniList's form only shows delete controls to data mods, so saved characters, staff, relations and links are removed from the **Custom Entry Tools** panel's Characters / Staff / Relations / External Links lists (✕ per row). Studio submissions are blocked from the server; nothing can ever reach AniList's moderation queue from a custom entry. The **Revision History** section works locally too: every local edit (native form Submit, quick-edit Save, staff / character / relation / link / tag changes) is logged on the record (`rec.history`, capped at 200) and served in the site's `revisionHistory` shape (action, changed fields, time, your avatar); entries without a log show a single CREATE row from their creation time. Pressing **Submit** ends with a “Custom entry saved locally” toast (the site's own message component, re-worded from “Submission successfully sent”) and returns to the **entry page** rather than the home page. On **mobile widths** (where AniList hides the rankings sidebar) a square tag-icon shortcut next to the favourite heart opens the same editor, and the whole UI, both modals, the quick-edit panel, toasts, lays out cleanly down to phone size.
- A **“Custom Entry Tools” panel at the top of the edit page** is the quick-edit home: title, format, release status, counts, cover (URL + MangaBaka cover picker), banner, description, genres, **tags** (`Name:rank`; AniList's form has no tag editor) and **studio** (studio submissions are blocked from the server), all saved with one button and mirrored into the native form below, which still handles the long tail (per-language titles, dates, synonyms, characters). The panel's **Save button is a convenience, not a requirement**: pressing the native form's **Submit** also applies any panel fields still pending (`flushPanelPending`, run by the `SaveMedia` interception) — dirty fields only, so a field edited only in the native form is never overwritten with the panel's stale copy, and for a field edited in both places the panel's value wins (its stale copy is dropped from the mutation's variables). The panel is laid out in bordered sections: the import search on top, **Details** (title, format, release status, counts, description, genres, tags, studio) and **Images** (cover URL + picker, banner URL) — the two groups the Save button covers (its tooltip says so) — then the immediate-save groups in the native form's own section order: **Airing Schedule** (anime), **Characters**, **Staff**, **Studios** (anime), **Relations**, **External Links**, and finally **Recommendations** (which has no form section; it's managed from the entry page). Rows for **local characters and local studios carry a pencil quick-edit button** (inline row: name / role / image URL for characters — a rename clears the stored Given/Surname parts; name / image URL / main flag for studios); real AniList characters/studios keep their served data, so only their form controls apply. The Studios section also has an **Add Custom Studio** row (name + optional image URL; AniList's own Add Studios only searches real studios): the first custom studio fills the Details Studio field (`media.studioName`, image in `media.studioImage`), further ones become `isCustom` links in `media.studios` with name-derived `studioId`s (same hash as the typed one, re-derived on rename), so they get working `/studio/<id>` pages, stats and search like the typed studio. Studio images are a panel-list decoration only — AniList's Studio type has no image field, so site pages can't show them. Panel rows without an image (studios, characters, staff) fall back to AniList's default no-image placeholder at render time (the same defaults the media page uses); nothing is stored. The same **MangaBaka/MAL import search** sits on top and applies immediately. A **Recommendations** block lists the entry's local recommendations (✕ to remove) and, for MangaBaka-linked entries, **Fetch From MangaBaka** auto-adds up to 10 similar series that map to real AniList entries.
- **Favourites show up on your profile**: favourited custom entries and characters are appended to the profile Favorites sections (overview and Favorites tab) client-side. **Reordering works too**: the reorder mutation is intercepted, custom ids are stripped before it reaches the server (real favourites still reorder server-side), and the full interleaved order is stored locally and re-applied, so a custom entry dragged to first place stays first. (On favourites lists spanning multiple pages of 25, custom entries stay appended at the end.)
- **Recommendations work natively**: Add Recommendation on a custom entry's page saves locally (no more "Internal Server Error"), rating buttons work, and the search offers **your other custom entries** alongside real media. Recommendation cards for real media use a locally captured stub, so they render offline. **Backlinks**: the real media you recommended from a custom entry shows the inverse card ("users also like → your entry") in its own recommendations strip and tab, and Add Recommendation on a **real** page offers your custom entries too; a pair is stored once (on the custom entry it was made from, or on the custom entry when the page's media is real) and rated from either side (`SaveRecommendation` with a custom `mediaRecommendationId`), and the card's delete (`DeleteRecommendation` on a local id) removes it. Custom ↔ custom pairs show on both entry pages.
- **Local reviews**: the sidebar **Write Review** button works on custom entries. AniList's own review editor (`/review/editor/<id>`) loads and saves locally (`SaveReview` / `RateReview` / `DeleteReview` answered from the record's `reviews`), the review renders on the media page's Reviews preview and tab, on its own `/review/<id>` page and in your profile's Reviews tab, and rating it locally moves the up-vote count. One review per user per entry, private reviews stay yours.
- **Dead-end native controls are hidden on custom pages**: the sidebar Edit button (functionally identical to our "Edit Custom Entry" button; its classes are `review button edit`, so it needs its own `.edit` rule — the pre-review `a.review.button` rule caught Write Review too), the Stats and Social tabs, and the always-empty Threads section. Write Review stays visible (reviews are local).
- **Relations**: the edit panel's **Fetch Relations From MangaBaka** turns MangaBaka's relationship data (prequel/sequel/side story/spin-off/alternative) into a native Relations section. Each related series links to **another custom entry** when one shares the MangaBaka id (with the reciprocal edge written back, so Sequel↔Prequel go both ways), to the **real AniList entry** when one exists, and otherwise a **custom entry is auto-created** from the MangaBaka data as a media-only record: it sits on no list (its page shows the native "Add to List" control) until you actually add it. Fetching is a **cursor, not a cap**: story-relevant types (sequels, side stories, spin-offs) are processed before parody doujins, 25 relations per click, and edges remember their MangaBaka id, so franchises with dozens of relations just take a few clicks ("N more to process; run again"). Edges are listed in the panel with ✕ to remove. **Adult content is handled like AniList handles it**: related series rated erotica/pornographic on MangaBaka are skipped entirely when your AniList account has 18+ disabled (the status line says how many), and included with `isAdult` set (native ADULT badge) when it's enabled. Imports also map MangaBaka's content rating and MAL's Hentai/Erotica genres onto `isAdult` now.
- **The sidebar “Add Tag” (+) works**: tags picked (or typed) in the native modal are added to the local record, spoiler flag included, and enriched from AniList's tag catalog (`MediaTagCollection`, cached a week in localStorage) with the real name casing, category, description and adult / spoiler flags. Imported tags get the same catalog fields at render time (in memory, nothing is rewritten), so hover descriptions and Stats-page grouping work; the hover bubble stays suppressed only for tags the catalog doesn't know. The **relevance dropdown** on each tag row (Main Theme .. Not Relevant, a 0-5 vote) sets the percentage directly (vote x 20), since a custom entry has exactly one voter.
- **Import search looks native**: results render like AniList's quick search (40px square cover, name over a "2003 Manga · Author" info line, solid blue hover) with a source badge per row. Thumbnails load with `referrerpolicy="no-referrer"` so hotlink-blocking hosts still show them.
- The **wrench manage modal** is laid out like AniList's own dialogs (header band, tabs, foreground body) with four tabs, five with developer options on: **Entries** (a search box in the quick search's idiom over a list in the media list's table idiom: cover, Title, Progress, Status, Type; click opens the entry page, the pen opens the native editor, the download icon copies that one entry as JSON to the clipboard, trash deletes), **Sync** (GitHub sync with a status card: a Sync row whose dot is green / pulsing amber / red for in-sync / syncing / error with a **Sync now** button, an Encryption row with its state and a Disable button, and manual syncs toast their result; plus a **Last pull** report listing which records the merge took from the other side: added / remote version won / deleted on remote), **Images** (image host, upload of embedded images with their count and size), **Settings** (Profile statistics, Search on top, Developer options toggles; with several accounts known, an **Accounts** selector choosing whose entries the Entries tab lists; Move to Another Account; Export / Import: Copy all / this account's as JSON to the clipboard, a paste box with **Merge Import** — combines the export with the current database the way a sync pull does, newest edit per record wins, tombstones respected — and **Replace database**; the Danger Zone that deletes every entry. Replace and Delete All open a GitHub-style confirmation where the word `confirm` must be typed; deletions are tombstoned so they sync) and **Debug** (only with developer options: **diagnostics** — script/db version, injection timing, worker and fetch hooks, RPC counters and leak tripwire, Vue store, account/owners, database size and embedded images, GitHub sync and image host reachability, GM_xmlhttpRequest, toggle state — with a copy button; the RPC logging switch; a leak-audit print). Actions report through AniList's own toast component.
- **Multiple AniList accounts**: entries and activities belong to the account whose list page you created them from. The manage modal's **“Move to Another Account”** block reassigns *everything* (entries, activities, and your replies on them) in one click, log into the other account and open its anime or manga list once so the script learns it, pick it in the dropdown, press **Move All**, and reload. Only accounts you've actually been **logged into** are offered as targets; owners of lists you merely browsed are pruned from the registry automatically (on load and during sync merges) unless they own entries. When more than one account is known, each row in the manage list shows which account it belongs to. The move propagates through GitHub sync like any other edit.
- **Clickable characters**: character cards link to a working local `/character/<id>` page (name, image, description, and an Appearances section back to the parent entry). Names display exactly as entered, no family/given reordering (matching AniList's own handling of multi-word names).
- **Local activity**: updating a custom entry generates client-side `ListActivity` records with AniList's exact wording, *watched episode / read chapter* on progress (+1 buttons included), *plans to watch/read*, *completed*, *paused watching/reading*, *dropped*, *rewatched/reread* while repeating. Consecutive progress updates merge into a range ("watched episode 3 - 5") within a 3-hour window, mirroring the server. A status change wins over a progress change in the same save, and progress edits on a **Completed** entry post nothing (so an entry created as Completed gets exactly one "completed X", not a "read chapter N of X" beside it). Activities appear at the top of the **home feed** (Following and Global) and your **profile feed**, respect the feed's type filters, and can be liked, replied to (plain text), subscribed, and deleted, all handled locally. Deleting a custom entry removes its activities.
- **Profile statistics**: custom entries count into your profile's numbers client-side, total anime/manga, episodes and days watched (days need a duration on the entry), chapters and volumes read, and the Stats pages' status / format / genre / release-year / start-year / country / tag / studio breakdowns (a 100-chapter entry read to the end adds 100 to Chapters Read), the **Activity History** heatmap (every local activity, past ones included; days keyed the way the server keys them, level colour recomputed for touched days), the Chapter / Episode Count chart (length buckets incl. Unknown), the Score breakdown and the mean score (custom scores converted from the account's score format to 0-100 and blended with the served mean, weighted by the served count; standard deviation stays as served), and the Stats pages' genre/tag/format… cards show the custom entries' covers (their cover-strip query is answered locally for custom ids, only real ids reach the server). Toggle it off in the wrench modal's **Profile statistics** block (per browser; default on).
- **Airing schedule + reminders**: the **Custom Entry Tools** panel of a custom **anime** has an **Airing Schedule** block (AniList's own form only shows its schedule section to mods): first episode's date/time, interval in days, episode count and starting episode → **Generate** writes `media.airingSchedule = [{airingAt, episode}]` (rows removable, **Clear** empties it; the native `airingSchedules` load / `SaveAiringSchedule` save are answered locally too). The next unaired item becomes `nextAiringEpisode`, so the media page shows the countdown and home cards / the list show "Ep N · in 3d" and behind counts. **Local notifications**: when a scheduled episode airs, an "Episode N of X aired." row appears in `/notifications` (All and Airing feeds) and the nav envelope counts it; entries created before a full start date get one "X started releasing today." row (Media feed) when that day arrives (catalogued-after-the-fact entries don't notify, 30-day window); and a full start / end date reached flips `NOT_YET_RELEASED → RELEASING` / `RELEASING → FINISHED` like the site does. Reminders are device-local (`al-custom-entries-notifs-v1`, not synced), generated lazily on the UI tick (`tickNotifications`, throttled to a minute), shown unread-first on page 1 and marked read when the All feed is opened; the viewer's `unreadNotificationCount` carries an `__alceUnread` marker so reruns adjust by the difference.
- **Staff/character auto-linking**: local staff and characters created by imports are auto-linked to their real AniList counterparts (`resolveRecPeople`, called after search-pick imports). Linking is conservative — `pickPersonMatch` requires an exact name match (either word order, or a listed alternative/native name) with exactly ONE matching search candidate, and single-token staff names (doujin circles) never link (`staffLinkable`); lookups are batched as aliased GraphQL fields (~14 per request, 700 ms apart), links are revision-logged and reversible in the native forms. Bulk import skips auto-linking (rate limits); re-picking an entry's source in the edit panel runs it.
- **Bulk import** (Settings → Bulk import): a **MyAnimeList export** (XML, or the `.xml.gz` via Choose file…; titles, type/format, progress, score, dates, notes, rereads carry over; details and covers are then fetched from the MAL API about one per second), your **MangaBaka library** (personal access token with `library.read`, used once and never stored; entries via `/v2/my/library`, series details via the public batch endpoint so the usual MangaBaka normalizer applies; state, progress, rating, dates, notes, private flag carry over), or a **CSV** (header row, any column order; see the hint in the modal for accepted column names; `score` is taken in the account's own score format). **Skip entries that exist on AniList** (default on) checks MAL ids against AniList in batches of 50 and honours MangaBaka's AniList link, so only what AniList lacks becomes a custom entry; rows already imported (same MAL / MangaBaka id) are skipped. Imports create no activities (`createRec({quiet})`), stamp `rec.imported`, embed covers afterwards and trigger a sync. Provider normalizers carry a `titles: {romaji, english, native}` field alongside the display `title` (MAL `title_english`/`title_japanese`, MangaBaka `romanized_title`/`native_title`/`secondary_titles.en`, MangaDex `title`+`altTitles` by lang, RanobeDB `romaji_orig`/`title_orig`/lang; CSV columns `romaji`/`english`/`native`); `importTitleObj` puts them in the media title's own fields (`userPreferred` is computed by `preferredTitleOf` from the viewer's AniList title language — `auth.options.titleLanguage`, romaji fallback — and recomputed on every DB load and title write, plus `tickTitleLanguage` on the 600 ms tick re-computes and re-commits all entities when the setting changes mid-session, so custom entries follow the setting like real ones without a reload; a CJK-dominant "english" — `looksCjk` — is treated as native, since MangaDex doujin entries often mislabel alt-title languages; `romajiScore` (Hepburn-syllable fraction) picks the real romaji when MangaBaka's `romanized_title` holds an English alt instead, and `pickEnglishTitle` chooses the English title from an untyped alt-title bag by token overlap with the romaji/display title (long vowels collapsed so Yuuka matches Yuka's) — shorter wins ties, zero overlap means null rather than a guess; a display title distinct from the romaji that is neither CJK nor romaji-scanning fills english, and the backfill revisits entries whose english is missing or merely mirrors the romaji; MAL synonyms, MangaDex alt titles and Dynasty aliases all feed it, and Dynasty titles/aliases are classified by script since the site has no language tags) and `stripTitleSynonyms` keeps them out of `synonyms`. Pre-1.42 imports flattened all four fields to the display title — `titleFlattened`/`applyTitleFix` heal such records when a re-run import hits a dupe row carrying titles; individual entries heal via a re-pick of their source in the edit panel. (The former Settings Backfill/Enrich buttons were removed in 1.44.4 once the import paths themselves produced correct data.) `createRec` and the quick-edit title save no longer fake english/native (null instead), so the media sidebar only shows real per-language rows; the quick-edit field shows `userPreferred` and writes the title-language field the viewer uses.
- **Backlinks**: real pages point back at the custom entries that reference them. A real entry related from a custom one lists that custom entry in its own Relations with the inverse type (Koiiro no Kyoukai shows “Same Universe · Tonight at the Mystia's Yatai”), a real AniList character linked from a custom entry lists it among their appearances (with the role), and a real staff person lists it under their roles (per media type) — all viewer-only, prepended, and repaired from the store when the page loaded before the hooks.
- **Search**: the search pages (`/search/anime|manga` with a text, genre/tag, format, status, country, year or on-list filter) and the header **quick search** include your matching custom entries (at their proper position when the sort has a value they carry, title / start date / chapters / episodes / volumes / id, at the very end for popularity / trending / score / favourites sorts, which a custom entry has no value for, and on top of the first page for relevance; the wrench modal's **Search** toggle instead pins them to the top of the results whatever the sort), and local characters show up in the quick search's Characters column, so a genre or tag link on a custom entry's page (or a Stats card) leads to a result set that contains it and links back to its page. The unfiltered popularity browse is left as served.
- **Home page "in Progress"**: custom entries with status Watching/Reading/Repeating are injected into the home page's *Anime in Progress* / *Manga in Progress* panels, most-recently-updated first, with working hover cards and **+1 progress buttons**.

## Image host (optional, recommended if you embed many covers)

Embedded `data:` images live inside the JSON database, so they count against `localStorage`'s ~5 MB quota and bloat the sync file. The companion server [al-custom-entry-images](https://github.com/johnthreekay/al-custom-entry-images) (currently a private repo) (a zero-dependency Node container, meant to sit behind cloudflared) takes those bytes instead: the script uploads to `POST /covers`, the server names the file by SHA-256 and serves it publicly with `Cache-Control: immutable`, and the record stores a plain URL. The database stays tiny, GitHub sync only carries text, and the only ceiling left is disk on your box.

- Set it up in the wrench modal, **Image host**: base URL (e.g. `https://sync.manga.example.com`) and the server's `UPLOAD_TOKEN`, then **Save & Test** (lists what's stored, proves the token). The token is stored in this browser's `localStorage`, like the GitHub token.
- Once configured, everything that would have been embedded (hotlink-blocked or decoy-serving hosts, RFP-safe paths, the quick-edit button, which now reads **Upload**) is uploaded instead. If an upload fails the script falls back to a `data:` embed and says so.
- **Upload embedded images** (same block) walks every entry, uploads existing `data:` covers/banners, rewrites the records to URLs and saves; reload afterwards. Source URLs (`coverSource`/`bannerSource`) are kept.
- Uploaded images are public at unguessable hash URLs and are not encrypted (the browser has to load them as images); only the database is E2E-encrypted in GitHub. Don't put Cloudflare Access in front of `/covers/*` GETs.

## Cross-device sync via GitHub (optional)

The wrench manage modal has a **GitHub sync** block. Once configured, every change is pushed (debounced a few seconds) to a JSON file in a private repo of yours, and every page load pulls and merges the remote state, so desktop and phone share one database. Merging is per-record: the newest edit of each entry/activity wins (timestamps are kept on every mutation), deletions replicate via tombstones instead of resurrecting, and entries created independently on two offline devices are both kept.

Setup (once):

1. Create a **private repo** on GitHub (e.g. `anilist-sync`). The file `data.json` is created on first sync.
2. Create a **fine-grained personal access token** (Settings → Developer settings → Personal access tokens → Fine-grained): repository access = *only that repo*, permissions = **Contents: Read and write**. Set a long expiration.
3. On each device, open the wrench manage modal → enter `youruser/anilist-sync` and the token → **Save & Sync Now**.

Notes:

- The token is stored in `localStorage` on anilist.co (the script runs with `@grant none`), so scope it to that one throwaway repo only.
- Sync happens on page load, ~4 s after any change, every 10 minutes, and on **Save & sync now**. Concurrent pushes from two devices are resolved by re-pulling and re-merging (the Contents API `sha` acts as a compare-and-swap). The page-load and 10-minute syncs take a **fast path**: when nothing changed locally since the last sync (`syncCfg.dirty`, set by every syncing save, cleared once the push or in-sync check lands) the script only asks the Commits API for the file's latest commit (`ghHead`, ~1 KB) and compares it with the one it last synced to (`syncCfg.remoteHead`, taken from the push response or looked up after a pull); the file is downloaded, decrypted and merged only when either side moved. Manual and change-triggered syncs always run the full path.
- Every sync is a git commit, so the repo doubles as versioned backup, you can recover any previous state from its history.
- Files over 1 MB come back from GitHub's Contents API without content; the script transparently reads them through the Git Blobs API instead (up to 100 MB). Embedded covers are stored once in the file (`medium`/`extraLarge` collapse to an `@large` marker on disk and expand on load), so an embedded cover costs its size once, not three times. Clients older than 1.29.3 don't expand that marker: update every device together.
- Descriptions (media and character) are stored as HTML and rendered natively, so the script **sanitizes them at render time** (tag/attribute allowlist, event handlers and non-http(s) URLs stripped). A tampered sync repo or a pasted import can therefore vandalize your data but not run script in your AniList session.

### End-to-end encryption (optional)

Set an **encryption passphrase** in the sync block and press **Save & sync now**: from then on `data.json` holds an **AES-256-GCM** envelope instead of plaintext. GitHub only ever stores ciphertext, and because GCM is authenticated, *any* tampering (or a wrong passphrase) makes decryption fail outright, a forged file is rejected before it can reach the merge. Enter the **same passphrase once on each device** (the key is derived with PBKDF2-SHA-256, 600k iterations; the salt travels in the envelope so every device derives the same key). The passphrase itself is never stored, only a **non-extractable `CryptoKey`** kept in IndexedDB.

- Sync behaviour is otherwise unchanged: same debounce, merge, tombstones, and `sha` compare-and-swap; pushes still happen only when content changed. The Sync tab's Encryption row shows whether the file is encrypted.
- Repo history stays a versioned backup, but as ciphertext: recover any old version with `ALcustom.decrypt(<pasted file content>)` in the console (add the passphrase as a second argument on a device without the key).
- **Update the script on all devices before enabling**, an old script version would misread the envelope and push plaintext over it (data self-heals via merge, but that commit is plaintext).
- Enabling does **not** rewrite old git history: previous plaintext commits remain readable. Recreate the repo (or squash history) if that matters to you.
- Your local data is always plaintext in the browser, so a forgotten passphrase costs nothing while any device still works, set a new one and re-push. Only "all devices gone **and** passphrase forgotten" makes the repo backup unrecoverable. The **Disable encryption** button decrypts, pushes plaintext again, and forgets the key.
- The passphrase is the privacy floor: anyone with the ciphertext can brute-force offline (slowed by the KDF), so pick a real one.

## Verifying nothing leaks to AniList

Open the browser console on any anilist.co tab and run:

```js
ALcustom.audit()
```

It prints a live tally for the session: how many custom-entry operations were **handled locally (never sent)**, how many **clean requests** were forwarded to AniList normally, and how many custom-id requests **leaked** to the network, which should always be **0**. The count is maintained by a tripwire on the real network paths (both the GraphQL Web Worker and `window.fetch`): every outgoing payload is scanned for a custom id (≥ 2,000,000,000) right before it would hit the wire, and any hit is logged as a loud `⚠ LEAK` error and recorded in `ALcustom.raw.leaks`. You can also confirm independently in DevTools → Network → filter `graphql`: editing a phantom entry (tags, characters, description, etc.) produces **no** POST whose payload contains its id.
- If the browser injects the script late (a Violentmonkey timing race; the Debug tab's diagnostics flag it), pages self-heal. The hooks patch responses on their way into the Vuex store; when a page's first queries ran before the hooks existed, `healFromStore()` (UI tick) re-runs every store-level patcher against the store — profile statistics and activity history, search pages, relation / character / staff / studio backlinks, profile favourites — all idempotent via membership checks or value markers, so repairs land whenever the initial responses arrive. `selfHeal()` (timed after load and after sync pulls) re-adds custom entries to list sections, home previews (fetching the rows' `updatedAt` itself when needed) and activity feeds, and a custom entry / character / staff / studio / review / edit page that briefly 404s is re-routed to its path within a couple of seconds.

### Completion behaviour

Mirroring the real AniList API: setting an entry to **Completed** auto-fills progress to the maximum episode/chapter (and volume) count and stamps today's date as start/finish, but **only when the series' release status is Finished**. Releasing/unreleased series are left untouched. Setting an entry to Watching/Reading stamps the start date if empty. The same applies to a fresh entry created with that status in the “+” modal. (Note: the native editor only sends *changed* fields, so this fires on the actual status transition, just like the real API.)

### Database versioning

The stored database carries `version` (currently 7). `migrateDB` runs on every load, import and merge result and fills in fields introduced later (activities, tombstones, favourite order, per-record `characters` / `staff` / `relations` / `recs` / `history` / `reviews` arrays, `media.externalLinks` / `tags` / `genres` / `synonyms` / `studios`), so new code can rely on the shape without scattered guards. Bump `DB_VERSION` and extend `migrateDB` when adding a field.

### Performance notes

- `saveDB` coalesces: any number of calls within one task serialize the database once at the end of that task (microtask), with a `pagehide` flush as a safety net, so imports, merges and multi-record saves don't re-stringify the whole database per record. `localStorage` is still written synchronously within the task, so there is no window for loss.
- Pure per-record render helpers are memoised where they parse: `sanitizeHtml` (DOMParser) caches by raw string, the heal pass caches parsed `<name>-{json}` page-key variables. The UI tick (600 ms) otherwise only does membership checks over the store, sub-millisecond at normal store sizes.
- Startup runs as one synchronous task (document-start), so the order of hook installation vs database load doesn't matter for the late-injection race; what matters is when the script manager injects (`__ALCE_T0`, shown in diagnostics).

### Tests

`node tests/run.js` runs the offline harness in `tests/`: each `*.test.js` extracts the pure functions it covers straight from the userscript source (`tests/lib.js`: `grabFunction`, `grabBetween`, `grabConst`, `evalBlock` with stubbed dependencies) and checks activity generation, staff linking, relations / external links, profile statistics + activity history (incl. idempotence across the store's partial merges), search placement, backlinks (relations, characters, staff, studios, recommendations), recommendation saves from either side, studios, reviews, airing schedule + local notifications, bulk import parsers (MAL XML, CSV) incl. per-language titles across every provider (synthetic fixtures per branch plus one labeled real-payload regression) and the flattened-title fix, tag canonicalization (synthetic catalog), staff import + exact-unique people-linking rules, and database migration / merge reports. Add a file per feature; keep the extraction markers (`/* --- staff --- */`, `const STAT_BUCKETS`, …) stable when refactoring.

### Developing / updating

With Violentmonkey's **“Allow access to file URLs”** enabled, install the script by opening `file:///…/anilist-custom-entries.user.js` and turning on **Track local file** on the install page, keep that tab open and any edit to the file re-installs automatically; just reload AniList. (Re-install can lag a few seconds behind a save, bump `__ALCE_VERSION` and check it in the console when in doubt.)

Set `localStorage.setItem('alce-debug', '1')` on anilist.co to log every worker RPC (query, variables, page/schema options, and response entity types), invaluable for discovering the normalized shapes a new page uses. `localStorage.removeItem('alce-debug')` turns it off.

## How it works

AniList's frontend does all its GraphQL through a per-request **Web Worker RPC** (`fetch(url, query, variables, headers, options)`) whose responses are [normalizr](https://github.com/paularmstrong/normalizr)-normalized entities merged into a Vuex store. The script:

- patches `window.Worker` and intercepts the RPC message channel:
  - `MediaListCollection` responses get your custom entries **injected in place** (as `listEntry` / `media` / `listSection` entities, including creating missing sections);
  - activity feed responses (page entities `homeActivity-*` / `userActivity-*`) get local `activity` entities **prepended**, and the home in-progress responses (`homeListPreview-ANIME/MANGA`) get custom `listEntry` ids **merged in by last-updated time** (the site's query only selects `id status score progress …` per row, so the outgoing query is extended with `updatedAt` first, otherwise every custom entry would pin to the top; when the page's query ran before the hooks existed, the self-heal path fetches `id updatedAt` for the preview's rows itself and re-sorts the panel);
  - `Media`, `SaveMediaListEntry`, `DeleteMediaListEntry`, and `ToggleFavourite` calls that reference a custom id are **answered locally** and never forwarded, as are activity interactions (`ToggleLikeV2`, `DeleteActivity`, `ToggleActivitySubscription`, `activityReplies`, `SaveActivityReply`, `DeleteActivityReply`, and the `/activity/<id>` permalink query) on local activities;
- patches `window.fetch` for the few mutations AniList sends from the main thread (e.g. `ToggleFavourite`), so custom ids can never leak to the server;
- commits section membership changes straight into the Vuex store (`setEntities`), so status changes move rows between lists instantly, without a reload.

Custom ids start at `2,000,000,000`, far above any real AniList media/entry id but still a valid GraphQL `Int`, so they can never collide with real data. Any unrecognized GraphQL request touching a custom id is blocked and answered with an empty payload as a safety net.

## Limitations

- Entries exist only in browsers where the script runs (use GitHub sync, or Export/Import, to share them across devices).
- After a sync pulls remote changes into an already-open tab, reload the page to see them everywhere (open list pages are only partially repaired live).
- Their activities are visible only to you, and they don't appear in other people's searches or site-wide rankings.
- Local activity replies are plain text (no markdown rendering).
- Site redesigns may change AniList's internal RPC/entity shapes and require script updates.
- Dynasty Reader search is HTML scraping (no JSON search endpoint), so a Dynasty redesign can break that one source until the selectors are updated.
- Embedded images live inside the JSON database: a few hundred embedded covers add several MB to `localStorage` and to the sync file, and `localStorage` is capped around 5 MB per origin, the script toasts if a save fails on quota. Prefer a hotlink-friendly URL when one exists (the cover picker's MangaBaka art always is).
